# Хранение состояния
1. Состояние приложения может храниться на сервере (server side) или на клиенте (client side). Но также состояние можно перенести на отдельные third-party сервера.
# Минусы хранения состояния в оперативной памяти
2. Минус хранения состояния в оперативной памяти - состояние храниться пока работает приложение. В случае, когда приложение требуется закрыть, то мы теряем все данные. Закрытие приложения требует и его перезапуск. Со стороны разработчика приложение может обновляться или мигрировать с одного сервера на другой, что требует его закрытия, а также могут наступить форс-мажоры со стороны ОС или хостера: обновление ОС, перенос серверов хостера или банальное обесточивание.
# Хранение состояния приложения в виде файлов (в постоянной памяти)
3. Изменение хранения состояния из оперативной памяти в виде файла (в постоянную память) избавляет от проблем с потерей состояния при закрытии/перезапуске приложения. Но состояние также храниться на стороне сервера.

Преимущества хранения состояния в виде файлов:
    1. Простота разработки приложения.
Недостатки хранения состояния в виде файлов:
    1. Необходимо создавать инфраструктуру для обработки данных в файлах: поиск, добавление, изменение и удаление полей;
    2. Файл в основном будет находиться в каталоге рядом с приложением, что ставит вопросы о безопасности;
    3. Необходимо отдельно создавать инфраструктуру шифрования/дешифрования данных;
    4. Часто используемые форматы .json, .yaml и др. не подразумевают хранения больших объёмов данных.

Помимо файлов можно перенести ответственность за управление и хранением состояния на СУБД.

Примущества такого подхода:
    1. Оптимизированные операции поиска, добавления, изменения и удаления полей;
    2. Доступ к данным защищён;
    3. Оптимизировано хранение данных.
Недостатки:
    1. Требуется разработки адаптера для работы с СУБД;
    2. Разработка адаптера зависит от типа СУБД и наличия ORM;
    3. Требуется уметь работать с API СУБД.
