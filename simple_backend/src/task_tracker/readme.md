# Хранение состояния в приложениях

## 1. Stateful vs Stateless архитектура

### Stateful (с сохранением состояния)
**Stateful** означает, что *сервер* хранит информацию о состояния клиента между запросами. Приложение запоминает данные сессии, историю действий юзера.

**Пример stateful:**
- Сервер хранит задачи в оперативной памяти (список Python)
- Сервер хранит задачи в локальном файле JSON
- Сервер хранит задачи в базе данных на том же сервере

**Характеристики stateful**
- Сервер "помнит" клиента между запросами
- Данные хранятся на стороне сервера (ОЗУ, файлы, БД)
- Сложнее масштабировать: нужно обеспечивать доступ к одним и тем же данным с разных серверов

### Минусы хранения состояния в оперативной памяти
1. Полная потеря данных при перезапуске
2. Ограничения по объёму памяти
3. Нет резервного копирования, невозможно восстановить данные после сбоя, нет истории изменений

### Хранения состояния в файлах (JSON в постоянной памяти)
По сравнению с оперативной памяти мы получаем следующие преимущества:
- Сохранность при перезапуске
- Доступ после обновления приложения
- Восстановление после сбоя
- Больший объём данных

Хранение состояния остаётся. Мы просто переместиили состояния из одного места в другое: данные всё ещё хранятся на сервере, сервер зависит от локального файла.

#### Примущества в общем:
- Не нужно устанавливать СУБД
- Не нужно настраивать подключение к БД
- Не нужен отдельный сервер БД и нет нужны за него платить
- Можно открыть файл в текстовом редакторе, соответственно легко отладить
- Простое резервное окпирование (copy-paste)

#### Общие недостатки:
- Race condition: несколько потоков одновременно обрабатывают запросы, что приводит к потерям данных; повреждение JSON (частичная запись)
- Отсустствие атомарности операций: чтение -> изменени в ОЗУ -> запись между этими операциями может вмешаться другой процесс
- Медленные операции при больших объёмах данных: чтение всего файла, необходимо перезаписывать весь файл при любом изменении
- Отсутствие безопасности
- Нельзя откатить изменения
- Нет сжатия данных

### Хранение в СУБД

#### Преимущества в общем:
- Оптимизированные операции: поиск по индексу, добавление записи, изменение записи
- Защита данных: транзакции, разграничение прав, шифрование, аудит
- Оптимизированное хранение: B-Tree индекс, Hash индекс, Composite индекс

#### Недостатки в общем:
- Сложность разработки
- Зависимость от типа СУБД: наличие ORM смягчает недостаток
- Накладные расходы: требование по объёму ОЗУ, нагрузка на CPU
- Необходимость администрирования: бэкапы, обновление версий, оптимизация запросов

### Stateless (без сохранения состояния)
**Stateless** означает, что каждый запрос независим и сервер не хранит информацию о предыдущих взаимодействиях. Все необходимые данные предаются в каждом запросе или хранятся во внешнем хранилище.

**Пример stateless:**
- Backend обращается к внешнему API (jsonbin.io, mockapi.io) за данными
- Каждый запрос содержит всю необходимую информацию (JWT токены)
- Сервер не хранит сессионные данные локально

**Характеристики stateless:**
- Каждый запрос самодостаточен
- Легко масштабировать: любой сервер может обработать любой запрос
- Отказоустойчивость: если один сервер упал, другой продолжает работу
- Данные хранятся на внешних сервисах (облачные БД, API)

**Важное уточнение**
Хранение данных в БД — это stateful подход:
- Данные сохраняются между запросами (состояние сохраняется)
- Сервер зависит от хранилища состояния (БД)
- Изменения в БД сохраняются и доступны следующим запросам

Однако Backend может быть stateless, даже используя БД, если:
- Backend не хранит состояние в своей памяти
- Каждый запрос обрабатывается независимо
- Состояние хранится во внешнем сервисе (БД), а не в приложении
- Любой экземпляр backend может обработать любой запрос, обращаясь к общей БД
